# M-5.4 — Recovery Strategy Classification

Tres niveles explícitos de recovery del runtime inmersivo. **Eliminar recovery implícito** = todo path que toca audio/visual/buffer debe declarar qué nivel ejecuta y por qué.

## Niveles

### 1. softRecover — corrección local, sin perder sesión

**Cuándo:** error transitorio que el runtime puede absorber sin intervención del usuario.

**Helper canónico:** mecanismos ya existentes — `audio_cache_invalidated` (INVARIANTE-9), `audioRetriedKeysRef.add` + reload via `load(index, true)`.

**Qué limpia:**
- Blob URL específico que dio duración inválida (NotSupportedError o duración < min).
- Una entrada de `audioCache` específica.

**Qué preserva:**
- `currentIdxRef.current`, currentIndex (React state).
- `contentSessionRef.current` (mismo session).
- `loadToken.current` (al ser una reload del mismo índice).
- Buffer de la machine (status, audioStarted, visualHighlightConfirmed).
- Player slots (`audioRefA`/`audioRefB`) y `activePlayer`.
- Cualquier executor sync activo (no se cancela; el reload no cambia chunk).

**Qué invalida:**
- Una entrada de audioCache (por key específica).

**Logs emitidos:**
- `audio_cache_invalidated`
- `PB_AUDIO_RETRY_ATTEMPT`
- `[CACHE_ENTRY_EVICTED]` (M-5.4)

**Reentry path:** `pb.load(currentIdx, true)` con retried mark — siguiente intento usa `getAudioUrl` que regenera el blob desde TTS.

---

### 2. hardRecover — reset del buffer pero mantiene sesión

**Cuándo:** drift de buffer/visual o ack faltante tras timeout (PB_RESUME_BOOTSTRAP_FAILED, audio_start_without_highlight, drift detected). NO es book switch.

**Helper canónico:** `hardResync(targetIndex, reason)` — `useImmersivePlayback.ts:~885`.

**Qué limpia:**
- `cancelPendingAdvance('skip_or_load')` — todos los timers de avance.
- `audioRefA.pause()` + `audioRefB.pause()` — detiene playback.
- Buffer de la machine → `bufferCancel('hard_resync')` (current=null, next=null, locked=false).
- Executor activo del SyncStrategyExecutor (via `cancelSyncStrategy` debería invocarse — verificar coverage en M-5.4).

**Qué preserva:**
- `audioCache.current` (NO invalida el cache de blobs).
- `contentSessionRef.current` (mismo session — diferencia clave con fullReset).
- `manifestRef`, `audioSentencesRef`, `toChunkRef`, `anchorsMapRef`, `audioModeRef`.
- React state del visor (sentences/audioSentences).
- audioFailedKeys / audioRetriedKeys (cross-content, persistente intra-session).

**Qué invalida:**
- Buffer de la machine entero.
- `loadToken.current++` (próximos awaits abortarán).
- `hardResyncAttemptsRef.current++` (cap en MAX_HARD_RESYNC_ATTEMPTS_PER_SESSION=2).
- Status del player → 'loading' (luego se decide vía load).

**Logs emitidos:**
- `hard_resync` (legacy log)
- `PB_HARD_RESYNC` (F6 canonical)
- `PB_BUFFER_CANCELLED { reason: 'hard_resync' }`
- `PB_HARD_RESYNC_CAPPED` si supera cap.

**Reentry path:** post-hardResync, el visor renderea, useLayoutEffect detecta `!isPreparedForIndex(currentIndex)` → `prepareSentence` → ack → ready para play manual.

---

### 3. fullReset — wipe completo, transición de contenido

**Cuándo:** cambio de libro (content.id change). NO es recovery, es transición. Pero está en la misma jerarquía conceptual: es el reset más fuerte.

**Helper canónico:** `pb.reset()` — `useImmersivePlayback.ts:~1900`.

**Qué limpia:**
- `cancelPendingAdvance('content_reset')`.
- `cancelSyncStrategy('content_reset')` (M-5.3.4).
- `cacheInvalidatedKeysRef.clear()`, `audioFailedKeysRef.clear()`, `audioRetriedKeysRef.clear()`.
- `hardResyncAttemptsRef.current = 0`.
- TODO el audioCache → `URL.revokeObjectURL` + clear.
- `abortCtrls` (abort all + clear).
- `inFlight` (clear).
- `audioRefA.src = ''` + `audioRefB.src = ''`.
- `currentIdxRef.current = 0`.
- `standbyReadyRef = false`.
- `sentenceStartTimeRef = 0`.
- Buffer de la machine → CONTENT_CHANGE dispatch → `initialState({contentId, sessionKey, startIndex: 0})`.

**Qué preserva:**
- Hooks (mismo componente vivo).
- `analyticsUserIdRef`.
- Engines externos (BlockEngine/RewardEngine/TranceEngine — el visor los maneja).
- DOM teleprompter (mismo `ImmersiveShell` instance).

**Qué invalida:**
- `loadToken.current++`.
- `contentSessionRef.current++` (KEY: todos los callbacks tardíos del libro anterior van a ser ignorados).
- `standbyGenRef.current++` (listeners canplaythrough viejos descartados).
- `setStatus('idle')`.
- React state `currentIndex = 0`.

**Logs emitidos:**
- `cleanup` (CONTENT_CHANGE de machine).
- `cancel_pending`.
- `[CACHE_ENTRY_EVICTED] via: 'reset_content_change'` (M-5.4).
- `[SYNC] cancel_via_runtime { reason: 'content_reset' }` (M-5.4).

**Reentry path:** el visor's content.id useEffect dispara setSentences(placeholder) → StartupEngine → post-hydration → `pb.load(targetIndex, false)`.

## Comparación tabular

| Aspecto | softRecover | hardRecover | fullReset |
|---|---|---|---|
| ContentSession se preserva | ✓ | ✓ | ✗ (++) |
| loadToken se preserva | ✓ | ✗ (++) | ✗ (++) |
| audioCache total | preserve | preserve | wipe all |
| audioCache entry | invalida 1 | preserve | wipe all |
| Buffer machine | preserve | wipe | wipe |
| Executor sync activo | preserve | cancel | cancel |
| Player.src | preserve | preserve | wipe '' |
| currentIdxRef | preserve | preserve | reset 0 |
| Status final | mantiene | 'loading' | 'idle' |
| Sentences/manifest | preserve | preserve | wipe + reload |

## Regla de uso

Cualquier path nuevo que toca lifecycle audio/visual debe declarar en el comment qué nivel ejecuta. Ejemplos:

```ts
// M-5.4 RECOVERY LEVEL: softRecover
//   - solo invalida audioCache[key] del blob defectuoso
//   - preserva session, buffer, executor
audioCache.current.delete(key);
URL.revokeObjectURL(blobUrl);
```

```ts
// M-5.4 RECOVERY LEVEL: hardRecover
//   - cancela buffer + timers + executor
//   - preserva audioCache + contentSession
hardResync(idx, 'manual_recovery_from_ux');
```

```ts
// M-5.4 RECOVERY LEVEL: fullReset
//   - libro cambió, wipe completo
pb.reset();
```

## Anti-patterns

❌ NO mezclar niveles en un mismo path. Si necesitás "wipe cache pero preservar buffer", agregá un nivel nuevo nombrado, NO inline la combinación.

❌ NO usar `setStatus('idle')` fuera de fullReset/reset.

❌ NO usar `contentSessionRef.current++` fuera de fullReset/reset.

❌ NO usar `hardResync` para book switch (es fullReset, no hardRecover).

❌ NO invalidar audioCache entera en softRecover (eso es fullReset/reset).

## Recovery NO automatizado en M-5.4

El watchdog (`runtimeWatchdog.mjs`) **NO ejecuta recovery automáticamente**. Solo emite warnings. Cualquier transición a recovery viene de:

1. Path determinístico del runtime (ej: NotSupportedError en `pActive.play().catch`).
2. Acción explícita del usuario (click play tras error, navegación entre libros).
3. Decisión del operador humano leyendo los logs y aplicando un fix de código.

Si en una iteración futura el watchdog necesita auto-recover, debe ser opt-in vía flag y siempre con downgrade explícito (ej: solo softRecover, nunca fullReset automático).
