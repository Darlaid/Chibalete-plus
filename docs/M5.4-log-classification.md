# M-5.4 — Log Classification

**Estado:** vivo. Este documento se cierra solo cuando los smokes A–G están corridos y los logs marcados `TEMP` o `REMOVE_LATER` quedan auditados con evidencia operacional real (no antes).

**Para qué sirve:** dictar qué logs sobreviven a M-5.5 (cleanup + staging gate) y cuáles se borran. La clasificación NO es opinión — está atada al subsystem que cubre, al riesgo que evidencia, y al ruido que genera.

**Política raíz:**

- **KEEP** — log permanente. Debería sobrevivir staging y producción. Útil si un usuario reporta un bug raro.
- **TEMP** — log de validación M-5.x. Permanece mientras corremos los smokes. Se evalúa al cerrar M-5.4.1 (estos serán los candidatos a borrar en M-5.5).
- **REMOVE_LATER** — log redundante/spammy/debug. Ya no aporta. Se borra apenas se validen los smokes.

## Reglas para nuevos logs (M-5.5 en adelante)

1. **Si emites un log nuevo, declarálo en este documento al mismo commit.** Logs sin clasificación serán removidos en cleanup.
2. **No emitas console.log dentro de hot paths** (loops de sentence, timer ticks, audio events) salvo que esté gateado por flag `immersive_debug` o `import.meta.env.DEV`.
3. **Prefiere `pbLog(...)`** que dual-emite a console + buffer telemetría — un log local sin telemetry casi siempre es candidato `TEMP`.
4. **Format `[TAG] mensaje`** con tag en MAYÚSCULA_SNAKE para que el filtro de DevTools funcione.

## Acción de cierre M-5.4.1

- [ ] Confirmar con operador que cada log `KEEP` aparece en al menos un smoke A–G como evidencia.
- [ ] Confirmar que ningún log `KEEP` aparece >1 vez por ciclo natural (ej. heartbeat 1/30s, no 1/100ms).
- [ ] Si algún log `TEMP` o `REMOVE_LATER` aparece en un smoke como **único** breadcrumb de un bug real → promoverlo a `KEEP`.
- [ ] Si algún log `KEEP` genera spam mayor a lo esperado → degradar a `REMOVE_LATER` y dejar nota acá.

Solo después de eso, M-5.5 puede arrancar el cleanup masivo.
