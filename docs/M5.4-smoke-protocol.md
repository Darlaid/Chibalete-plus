# M-5.4 — Browser Smoke Protocol

Checklist formal para validar resilience del runtime inmersivo antes de cualquier deploy. **Cada smoke se corre manualmente en browser real con DevTools abierto**.

Antes de empezar: abrí DevTools → Console. En el filter pegá:
```
[M53_ACK] | [M532_ | [SYNC] | [CACHE_ | [OWNERSHIP_ | [WATCHDOG_ | [PB_AUDIO_MODE] | PB_HARD_RESYNC | PB_BUFFER_CANCELLED
```

Antes de cada smoke, ejecutá en la console:
```js
window.__pbDiag = () => console.dir(pb.getRuntimeDiagnostics(), { depth: null });
```
(reemplazá `pb` con el handle real si está expuesto vía window).

---

## Smoke A — Alicia 15 min playback continuo

**Setup:** abrir Alicia desde inicio. Confirmar que carga.

**Acciones:**
1. Click Play.
2. Dejar correr ininterrumpido 15 min.
3. Cada 3 min: `window.__pbDiag()` y screenshot del snapshot.

**Validar:**
- ✓ `[PB_AUDIO_MODE] perSentence` (o el modo real detectado)
- ✓ `[CACHE_ENTRY_CREATED]` aumenta gradualmente, `[CACHE_ENTRY_EVICTED]` también (GC funciona)
- ✓ `cacheEntries.audioCache` se mantiene <50 al final
- ✓ `hardResyncCount === 0`
- ✓ `ownershipTokens.ownershipViolationCount === 0`
- ✓ NO aparece `WATCHDOG_*` warning crítico
- ✓ `currentSentence` avanza monotónicamente
- ✓ `lastVisualAckAt`, `lastAudioEventAt` siempre dentro de los últimos 10s

**Falla si:**
- ✗ Cache size sigue creciendo después de minuto 5 (no se evictan).
- ✗ Algún `WATCHDOG_STALLED_AUDIO` durante playback continuo.
- ✗ `PB_HARD_RESYNC` se dispara sin causa real.

## Smoke B — Guerra de los mundos 15 min (chunked)

**Setup:** abrir Guerra. Confirmar log `[PB_AUDIO_MODE] perChunkNoAnchors (degraded)`.

**Acciones:**
1. Click Play.
2. Dejar correr 15 min.
3. Observar logs `[SYNC] SYNC_SENTENCE_ACTIVATE` y `CHUNK_AUDIO_REUSE`.

**Validar:**
- ✓ `[SYNC] CHUNK_NO_ANCHORS_HEURISTIC` aparece UNA vez por chunk audio.
- ✓ `[SYNC] HEURISTIC_TIMELINE_BUILT` aparece UNA vez por chunk.
- ✓ `[SYNC] SYNC_SENTENCE_ACTIVATE` para cada frase del chunk (no doble).
- ✓ `CHUNK_AUDIO_REUSE` aparece cuando se avanza dentro del chunk.
- ✓ Audio NO se reinicia al avanzar frase (escuchá: continuidad sonora).
- ✓ Visual avanza frase a frase (no queda pegado).
- ✓ Al cambiar a nuevo chunk: `[SYNC] cancel_via_runtime { reason: 'load_new_audio' }` + nuevo SYNC_STRATEGY_EXEC_START.

**Falla si:**
- ✗ Doble `SYNC_SENTENCE_ACTIVATE` para mismo `sentenceIdx`.
- ✗ Audio se reinicia desde 0 al avanzar frase dentro de chunk.
- ✗ `OWNERSHIP_VIOLATION` aparece (executor anterior no se canceló).
- ✗ `HEURISTIC_DURATION_UNAVAILABLE` repetido.

## Smoke C — Cambio rápido entre libros (book switch torture)

**Setup:** abrir Alicia.

**Acciones:**
1. Click Play, esperar 5s.
2. Navegar a Guerra. Click Play, esperar 5s.
3. Navegar a otro libro. Click Play, esperar 5s.
4. Repetir el ciclo 20 veces. Total ~5 min.

**Validar:**
- ✓ Cada switch emite `[SYNC] cancel_via_runtime { reason: 'content_reset' }`.
- ✓ Cada switch emite `[CACHE_ENTRY_EVICTED] via: 'reset_content_change'`.
- ✓ `cacheEntries.audioCache` vuelve a <10 después de cada reset.
- ✓ `ownershipTokens.contentSession` aumenta en 1 por cada switch.
- ✓ NO aparece `WATCHDOG_DESYNC_WARNING`.
- ✓ NO aparece callback con contentId del libro anterior tras switch (buscar PB_LATE_VISUAL_ACK_IGNORED — debería ser raro pero esperable).

**Falla si:**
- ✗ Memoria del browser crece >100MB durante el ciclo.
- ✗ Audio del libro anterior sigue sonando >500ms tras switch.
- ✗ Visual mezcla sentences de dos libros.

## Smoke D — Pause/Resume spam (30 toggles)

**Setup:** Alicia o Guerra, posición media.

**Acciones:**
1. Click Pause → Resume → Pause → Resume... rápidamente, 30 veces.
2. Mirar el snapshot `window.__pbDiag()` después.

**Validar:**
- ✓ Al final, `playbackState.status === 'paused'` o `'playing'` consistente con último click.
- ✓ `activeTimers.pendingAdvance === false` y `pendingFallback === false` (todos los timers limpios).
- ✓ `[M53_ACK] emit` NO entra en loop (debería ser pocos, idempotente).
- ✓ NO doble `play_start` para mismo índice.

**Falla si:**
- ✗ `WATCHDOG_TIMER_LEAK`.
- ✗ Audio doble (dos voces hablando).
- ✗ `OWNERSHIP_VIOLATION`.

## Smoke E — Background tab 5 min

**Setup:** Alicia o Guerra reproduciendo normalmente.

**Acciones:**
1. Click Play, esperar 10s para confirmar avance normal.
2. Cambiar de tab (Cmd+T / Ctrl+T y dejar otro tab activo).
3. Esperar 5 min.
4. Volver al tab original.

**Validar:**
- ✓ Audio continuó (o pausó, según política del browser).
- ✓ Al volver: `currentSentence` consistente con audio actual.
- ✓ NO burst de `SYNC_SENTENCE_ACTIVATE` repetidos (browser throttling de setTimeout no debería causar avalancha).
- ✓ NO `replay cascade` (mismo audio reproduciéndose múltiples veces).
- ✓ `WATCHDOG_STALLED_AUDIO` ES esperable durante background si el browser pausó — debería desaparecer al volver.

**Falla si:**
- ✗ Tras volver: visual y audio desincronizados >5 frases.
- ✗ Múltiples executors viven (`OWNERSHIP_VIOLATION`).
- ✗ Cache creció >100 durante background.

## Smoke F — Network throttling (Slow 3G)

**Setup:** DevTools → Network → Slow 3G.

**Acciones:**
1. Abrir libro nuevo (sin cache previa).
2. Click Play.
3. Dejar reproducir 5 min con throttling activo.

**Validar:**
- ✓ TTS fetch tarda más pero NO timeoutea spurious (20s timeout vigente).
- ✓ NO aparece `WATCHDOG_HARD_RESYNC_CASCADE`.
- ✓ Visual NO se adelanta al audio (el `pb.load` espera el getAudioUrl antes de avanzar).
- ✓ Status `'loading'` se mantiene visible hasta que llega el audio.

**Falla si:**
- ✗ TTS timeout dispara `PB_AUDIO_UNRECOVERABLE` siendo que la red está lenta no rota.
- ✗ Audio doble al recibir respuestas late.

## Smoke G — PlaybackSpeed changes (0.75x → 1.5x)

**Setup:** Alicia reproduciendo.

**Acciones:**
1. Cambiar speed a 0.75x. Esperar 1 min.
2. Cambiar a 1.5x. Esperar 1 min.
3. Cambiar a 1.25x. Esperar 1 min.

**Validar:**
- ✓ Audio cambia velocidad inmediatamente sin reload.
- ✓ Visual sigue sincronizado (en chunked mode el executor usa `audio.currentTime` que escala automático con `playbackRate`).
- ✓ NO doble `SYNC_SENTENCE_ACTIVATE`.
- ✓ NO `PB_AUDIO_STARTED_REJECTED` por velocidad.

**Falla si:**
- ✗ Pop/click al cambiar velocidad.
- ✗ Visual se atrasa o adelanta del audio.

## Criterio de cierre M-5.4

Los 7 smokes A–G deben pasar SIN ningún ✗. Adicional, durante todos los smokes:

| Métrica | Esperado |
|---|---|
| `WATCHDOG_STALLED_AUDIO` | 0 (excepto Smoke E durante background, si browser pausó) |
| `WATCHDOG_STALLED_VISUAL` | 0 |
| `WATCHDOG_DUPLICATE_OWNERSHIP` | 0 |
| `WATCHDOG_TIMER_LEAK` | 0 |
| `WATCHDOG_DESYNC_WARNING` | 0 |
| `WATCHDOG_CACHE_RUNAWAY` | 0 |
| `WATCHDOG_HARD_RESYNC_CASCADE` | 0 |
| `PB_HARD_RESYNC` | <= 2 por sesión (cap) |
| `OWNERSHIP_VIOLATION` | 0 |
| `tts_fail` con error/message undefined | 0 (M-2.7 fix) |
| Memoria browser growth durante 15 min | <30 MB |

## Lo que NO probamos en M-5.4

- Concurrencia entre múltiples usuarios (eso es backend).
- Acepto/Rechazo de TTS providers degradando (eso lo cubrió M-2.7).
- Visual parity (M-5 / M-5.1).
- V2 dev visor (`/visor-v2-local/`) — fuera de alcance del smoke productivo.

## Próximos pasos post-smoke

Si los 7 smokes pasan:
1. **Cleanup de logs temporales** (`[M53_*]`, `[M532_*]`, `[AUDIO_TRACE]`) — patch pendiente en M-5.4.x.
2. **Validar typecheck + lint en CI**.
3. **Decisión de staging** (no incluida en M-5.4 — separate ticket).

Si algún smoke falla:
1. Capturar snapshot completo de `getRuntimeDiagnostics()` justo al fallo.
2. Filtrar logs por `[WATCHDOG_*]` y `OWNERSHIP_*` — esos son los breadcrumbs primarios.
3. NO intentar fix masivo — clasificar la falla por nivel de recovery (soft/hard/full) usando `docs/M5.4-recovery-strategy.md`.
