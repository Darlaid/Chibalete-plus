# M-4.3 — Audio Contract Audit & Instrumentation

Sprint Inmersivo V2 / Fase M-4.3 — diagnóstico granular del pipeline
`AudioRuntime ↔ provider ↔ HTMLAudioElement` para identificar el ROOT CAUSE
exacto de `audio_contract_failed`.

**Contexto**: M-4.2 confirmó que `play()` produce `audio_contract_failed` con
errorMeta vacío. Esa kind se emite cuando `AudioRuntime.startPlayback()`
rechaza con reason `play_rejected | factory_throw | factory_invalid` (NO
`autoplay_blocked`). Sin instrumentación granular era imposible discriminar
entre los 3.

---

## 1 · Contrato formal `AudioAcquireResult`

Definido en `engines/AudioRuntime.d.ts`:

```typescript
interface AudioAcquireResult {
  ok:               boolean;
  url?:             string;
  durationMs?:      number;
  mimeType?:        string;
  preloadSource?:   'cache' | 'network' | 'tts';
  errorKind?:
    | 'no_src'         // resolveSrc devolvió null / empty
    | 'invalid_url'    // resolveSrc devolvió non-string o string vacío
    | 'factory_throw'  // audioFactory lanzó
    | 'factory_invalid' // audioFactory devolvió no-Audio-like
    | 'load_failed'    // event 'error' del HTMLAudioElement pre-play
    | 'play_rejected'  // audio.play() rechazó (no autoplay)
    | 'autoplay_blocked' // NotAllowedError / autoplay policy
    | 'cancelled'      // closeSession durante acquire
    | 'unknown';
  errorMeta?: {
    provider?:           'cache' | 'manifest' | 'tts' | 'unknown';
    requestedIndex?:     number;
    requestedSentenceId?: number;
    resolvedUrl?:        string | null;
    preloadState?:       string;
    browserError?:       string | null;
    playPromiseError?:   string | null;
    readyState?:         number;
    networkState?:       number;
  };
}
```

NO se construye este objeto directamente — `preflight` + `startPlayback` emiten
**diagnostics granulares** con campos individuales, y el caller (session) los
agrega en `lastError.meta`. Este interface documenta la SEMÁNTICA del flujo.

## 2 · Pipeline instrumentado — 10 + 1 diagnostic kinds

Familia `audio.acquire.*` emitida por `AudioRuntime` (`engines/AudioRuntime.mjs`):

| Diagnostic kind | Cuándo | Payload key |
|-----------------|--------|-------------|
| `audio.acquire.request` | preflight() invocado | `{index}` |
| `audio.acquire.provider` | resolveSrc invocado | `{index, providerKind}` |
| `audio.acquire.url` | resolveSrc devolvió string válido | `{index, src, srcPreview, srcLength}` |
| `audio.acquire.null_url` | resolveSrc devolvió null/undefined | `{index, src}` |
| `audio.acquire.invalid_url` | resolveSrc devolvió no-string/empty | `{index, srcType, srcLength}` |
| `audio.acquire.load_start` | factory OK + src asignado, antes de play() | `{index, src, srcPreview, readyState, networkState}` |
| `audio.acquire.canplay` | event 'canplay' del HTMLAudioElement | `{index, readyState, networkState}` |
| `audio.acquire.play_resolved` | audio.play() Promise resolved | `{index, readyState, networkState}` |
| `audio.acquire.play_rejected` | audio.play() Promise rejected | `{index, reason, errorName, errorMessage, isAutoplayBlocked, readyState, networkState}` |
| `audio.acquire.exception` | throw en cualquier fase (preflight/factory/set_src) | `{index, phase, errorName, errorMessage}` |
| `audio.acquire.cancelled` | closeSession durante acquire (post-stale) | `{index, phase, reason, audioWasAcquired}` |

Cada uno se re-emite por el viewer como `[V2] audio.acquire.*` en consola, con
`console.log` para los OK paths y `console.warn` para los fail paths
(`null_url`, `invalid_url`, `play_rejected`, `exception`).

## 3 · errorMeta propagado a `lastError`

`ImmersiveSession.mjs` ahora agrega el `meta` del `startPlayback` result al
`lastError.meta` (campos `src, requestedIndex, requestedSessionId,
browserError, playPromiseError, readyState, networkState`).

El viewer logea `[V2] playback.audio.acquire.fail` con TODOS los campos
expuestos individualmente para inspección inmediata sin expandir objetos:

```js
{
  sessionId, index, errorKind,
  reason, requestedIndex, requestedSessionId, resolvedUrl,
  browserError, playPromiseError, readyState, networkState
}
```

## 4 · Diagnostics subscribe API (nuevo)

`engines/Diagnostics.mjs` ahora expone `subscribe(listener) → unsubscribe`.
Listeners se invocan POST `log()` con event frozen. Backward-compatible:
si no hay listeners, performance idéntica al sink puro.

```typescript
const unsub = stack.diagnostics.subscribe((event) => {
  if (event.kind.startsWith('audio.acquire.')) {
    console.log(event.kind, event.data);
  }
});
```

El viewer V2 usa esto para re-emisión automática en consola.

## 5 · Close-during-acquire — fix de zombie audio

**Bug detectado durante audit**: si `closeSession` (vía `forceClose` /
`runtime.destroy`) corre durante `await audio.startPlayback()`, el audio
acquired exitosamente queda zombie en `AudioRuntime.activeAudio` (el
`releaseFor` en `_close` corre ANTES de que la promise resuelva, encontrando
`activeKey === null`; cuando resuelve, asigna activeKey al closed session).

**Fix aplicado** en `_play` y `_resume`:

```js
try { assertLive(captured, 'play.startPlayback'); }
catch (e) {
    if (start.ok) {
        try { audio.releaseFor(sessionRef); } catch { /* ignore */ }
    }
    diag('audio.acquire.cancelled', { ... });
    return { ok: false, error: e };
}
```

Si el `assertLive` post-startPlayback throws (stale), y `start.ok === true`
(audio fue acquired exitosamente), explícitamente liberamos antes de retornar.

`audio.acquire.cancelled` se emite siempre en este path, con `audioWasAcquired`
flag indicando si hubo cleanup real o no.

## 6 · canplay invariant — STATUS

**Propuesta del spec**: AudioRuntime NO debe transitar a `playing` hasta
confirmar `canplay`.

**Estado actual M-4.3**: canplay event se **registra** como diagnostic (best-
effort, `once: true` listener). NO se gate-a el `startPlayback` resolution.

**Razón**: gate-ar requeriría modificar test mocks (mock audio no dispatcha
canplay). Diferido a sprint dedicado post-smoke productivo.

**Lo que sí está implementado**: el log `[V2] audio.acquire.canplay` aparece
en consola cuando el HTMLAudioElement productivo emite el event. Permite
verificar manualmente si play_resolved llega ANTES o DESPUÉS del canplay.

### S2 — Identificar root cause del audio_contract_failed actual

Si la sesión M-4.2 producía `audio_contract_failed`, en M-4.3 ahora se va a
ver UNO de estos paths antes del fallo:

| Log de fallo | Diagnóstico | Próximo paso |
|--------------|-------------|--------------|
| `audio.acquire.null_url` | El resolver devolvió null (manifest miss + TTS fallback fail) | Investigar manifestAdapter / TTS endpoint |
| `audio.acquire.invalid_url` | Resolver devolvió tipo inválido | Bug en `resolveAudioSrc` o cache preload |
| `audio.acquire.play_rejected { reason: 'play_rejected' }` | Browser rechazó play() por otro motivo (CORS, decode pre-play, src inválida post-set) | Inspeccionar `browserError`, `playPromiseError`, `readyState` |
| `audio.acquire.exception { phase: 'factory' }` | `audioFactory` lanzó | Bug en audioAdapter.factory wiring |
| `audio.acquire.exception { phase: 'set_src' }` | Asignación `audio.src = src` lanzó | Bug en HTMLAudioElement / src malformada |

## 9 · NO implementado en M-4.3 (deferred)

- **canplay gating** — registrado como diagnostic, NO bloquea play_resolved.
  Requiere actualizar test mocks. Diferido a M-4.4 (post smoke productivo).
- **AbortSignal en startPlayback** — currently el cancel es vía session
  token bump + assertLive post-await. Sin AbortSignal nativo, el audio
  Promise sigue ejecutándose hasta resolver — sólo previene state mutation
  post-resolve. Suficiente para single-audio policy, no para shutdown
  inmediato. Diferido.
- **mediaError → audioAcquireResult.errorKind 'load_failed'** — actualmente
  el event 'error' del HTMLAudioElement se procesa en otro path
  (`audio_failed`, `audio_decode_failed`). No se integra al
  AudioAcquireResult contract en este sprint. Diferido.
- **Visual parity / sentence highlighting** — fuera de scope M-4.3.
- **V1 migration / production rollout** — fuera de scope.
