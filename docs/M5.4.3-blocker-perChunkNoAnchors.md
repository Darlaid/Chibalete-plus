# M-5.4.3 — BLOCKER fix: perChunkNoAnchors avance visual

**Estado:** fix **EXTENDIDO** (segunda iteración). Primer fix cubría solo `audio.duration` race en el executor; el blocker seguía abierto porque el **spawn nunca corría** en ciertos paths (`resume()` y `handleEnded` gapless). Esta iteración consolida los 3 sitios de `.play()` en un único helper `onAudioPlaybackStarted`. **Validación browser sigue pendiente.**

## Iteración 2 — root cause real

Auditoría del hook detectó **3 sitios de `.play().then()`** y solo uno spawneaba executor:

| Path | Función | Antes de M-5.4.3 iter 2 |
|---|---|---|
| `pActive.play()` | `load()` autoplay | ✅ Spawn presente |
| `p.play()` | `resume()` | ❌ **Sin spawn** — bug |
| `nextEl.play()` | `handleEnded()` gapless | ❌ **Sin spawn** — bug |

Para Guerra (perChunkNoAnchors), el path típico es:
- Click inicial → `load()` autoplay → spawn ✓ → primer chunk avanza
- Fin del chunk_0 → `handleEnded()` → gapless `nextEl.play()` → **sin spawn** → siguiente chunk reproduce audio pero NO avanza visual
- Si usuario pausó/reanudó → `resume()` `p.play()` → **sin spawn** → audio reproduce pero NO avanza

Esto explica todos los síntomas reportados (audio sí, texto no, `M53_ACK skipped runtime_already_confirmed` en loop, ningún `SYNC_SPAWN_*`).

### Helper unificado

`onAudioPlaybackStarted(audioEl, index, callsite)` centraliza:
1. `[PB_SPAWN_CALLSITE]` log con audio state completo
2. `lastAudioEventAtRef` + `lastChunkTransitionAtRef` (watchdog timestamps)
3. `dispatchMachine({ type: MA.AUDIO_STARTED, index })`
4. `spawnSyncExecutorIfChunked(audioEl, index, callsite)`

Llamado desde los 3 sitios:
- `load_autoplay` — `pActive.play().then(...)` (load)
- `resume` — `p.play().then(...)` (resume) ← **fix nuevo**
- `gapless_advance` — `nextEl.play().then(...)` (handleEnded) ← **fix nuevo**

### Dedup (anti-doble-spawn)

`spawnSyncExecutorIfChunked` ahora chequea, antes de crear executor:
- Si hay un handle vivo con mismo `sessionId` Y mismo `_chunkKey` → log `SYNC_SPAWN_SKIPPED { reason: 'already_alive_same_chunk' }` y return.

Cada handle nuevo se etiqueta con `_chunkKey` al crearlo. Evita el caso "resume() tras pause() en la misma frase" que recrearía executor sin razón.

### Lazy mode derivation

Si `ctx.audioModeRef.current === null` cuando ocurre el spawn (race posible en book-switch), el spawn deriva el modo on-the-fly:

```ts
deriveAudioModeLazily(): 'perSentence' | 'perChunkWithAnchors' | 'perChunkNoAnchors' | null
```

Reglas (en orden):
1. `sentenceToChunk` vacío → null (no podemos decidir, spawn aborta con SKIPPED)
2. `chunkKey === sentenceIdx` para todos → `'perSentence'`
3. Hay anchors con `startMs` finito → `'perChunkWithAnchors'`
4. Resto → `'perChunkNoAnchors'`

Emite `[SYNC_MODE_NOT_READY_AT_PLAY]` con `derivedMode` y persiste el resultado en `ctx.audioModeRef.current` para próximos spawns.

## Hipótesis confirmada (sin browser, por lectura de código)

El executor en `utils/syncStrategyExecutor.mjs` tenía un agujero en `perChunkNoAnchors`:

1. Si `audio.duration` era `NaN`, `Infinity` o `0` al spawn → engagaba path B (esperar `loadedmetadata` 2s).
2. Si tras 2s la duración seguía mala → llamaba `cancel()` → **no se construía timeline ni se instalaban listeners** → no avanzaba nada para siempre.

Esto se da en V2 chunked MP3 cuando el navegador reporta `duration=Infinity` hasta que termina de bufferear. El audio reproducía igual porque para reproducir no se necesita la duración real.

## Fix aplicado

### 1. `utils/syncStrategyExecutor.mjs`

- **Fallback word-count** cuando duration sigue mala tras el timeout:
  - Función nueva: `buildFallbackTimeline(sentenceGroup, playbackSpeed)`.
  - Estima cada frase usando `13.5 chars/sec` (≈150 wpm en español) escalado por playbackSpeed.
  - Piso por frase: `1200ms` (también escalado por speed).
  - Esto NO cancela el executor — instala los listeners de `timeupdate`/`ended` y permite que el audio real (cuando avance) dispare activaciones progresivas.
- **Tick inmediato post-spawn** ya existía (`tickActivate(initialMs, 'initial_tick')`), pero ahora también corre en el path de fallback (`spawn_immediate_fallback`).
- **Logs diagnósticos** nuevos (todos visibles al filtrar por `HEURISTIC_` en DevTools):
  - `HEURISTIC_EXEC_ENTER` — al entrar al branch perChunkNoAnchors, con duration/readyState/paused/currentTime/speed.
  - `HEURISTIC_WAIT_METADATA` — cuando se cuelga listener loadedmetadata.
  - `HEURISTIC_METADATA_READY` — cuando loadedmetadata dispara.
  - `HEURISTIC_TIMELINE_BUILT` — ahora incluye `via: 'duration_ready_at_spawn' | 'metadata_event' | 'fallback_word_count'`.
  - `HEURISTIC_DURATION_FALLBACK_USED` — fallback engaged (con timeline completa para inspección).
  - `HEURISTIC_DURATION_UNAVAILABLE.decision` — ahora dice `'engage_fallback_word_count'`, antes decía `'degraded_no_internal_advance'`.

### 2. `hooks/useImmersivePlayback.ts`

- En `spawnSyncExecutorIfChunked`, antes de cualquier validación:
  - `SYNC_SPAWN_ATTEMPT` — con todos los campos pedidos (index, contentId, mode, chunkKey, audioDuration, audioReadyState, audioPaused, audioSrc, audioCurrentTime, sessionId).
- Skipped paths:
  - `SYNC_SPAWN_SKIPPED` con `reason: 'no_audio_element' | 'mode_not_chunked'`.
- Success / failure:
  - `SYNC_SPAWN_SUCCESS` — agrega `sentenceGroupLen` y `anchorsLen`.
  - `SYNC_SPAWN_FAILED` — incluye `error.message`.
- En `advanceWithinChunk`, al inicio:
  - `ADVANCE_WITHIN_CHUNK_CALLED` con `fromIdx`, `toIndex`, `fromChunk`, `toChunk`, `sameChunk`, `statusBefore`, `bufferIndexBefore`, `audioMode`, `sessionId`.
